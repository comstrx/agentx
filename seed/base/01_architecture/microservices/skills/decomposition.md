# Decomposition

Carving services out of a working monolith — the craft of cutting without bleeding.

- **Extraction is evidence-driven, one seam at a time:** the candidates name themselves with numbers — a module scaling differently (10× the traffic of the rest), deploying on a different rhythm, isolating a risk (the PCI surface), or owned by a team blocked on the shared release train. No number, no extraction.
- **The monolith's discipline decides the cost:** a module already behind a port (capability interface, events out, no foreign table reads) extracts in days; a module reaching into siblings' tables extracts in quarters — the extract-ready law inside the monolith IS the microservices migration plan, paid in advance.
- **The strangler sequence, in order:** (1) carve the seam inside the monolith (port + events, kill foreign reads) → (2) split the DATA: the module's tables move behind its interface, foreign keys across the seam become ids + read models → (3) stand the service up beside the monolith, shadow traffic to it, compare → (4) cut over with a switch, keep the fallback warm → (5) delete the monolith's copy the release AFTER cutover proves out.
- **Data separation is the real project — the code move is a Tuesday:** shared tables are the coupling; the sequence per table is expand (service gets its own copy/ownership) → double-write with the outbox → backfill → switch reads → contract. Cross-boundary JOINs become either a read model the consumer builds from events or an API composition — chosen per query, measured for the N+1-over-network trap.
- **The first extraction buys the platform:** correlation-id tracing, contract tests, deploy pipeline, service scaffold, outbox machinery — priced into service #1, amortized by every later one. A first extraction estimated without the platform bill is a lie that poisons the roadmap.
- **Shared code is resolved, never half-shared:** the extracted service takes a COPY of the small stuff (casts, helpers — divergence is fine), a LIBRARY of the truly stable (envelope, event schemas), and NOTHING of the domain — a shared domain library between services is the monolith's coupling wearing a package manager.
- **Authorization crosses as claims, not lookups:** the service trusts the verified token/context (actor, tenant, permissions relevant to it) — a service calling back "may this actor…?" per request has recreated the monolith's coupling with latency; permission models that cannot be claimed yet are a signal the seam is premature.
- **Reversal is a designed option:** shadow phase metrics (correctness diff, latency, error rate) gate each step; the fallback path stays alive until the service survives a real incident — extractions that cannot roll back are bets, not engineering.
- **Merge is a success too:** two services that always deploy together, share a release calendar, and fail together get re-merged without shame — the goal is boundaries that pay rent, and the map is redrawn by evidence in both directions.
- The anti-pattern gallery, named at review: the distributed monolith (shared DB, sync call chains) · the nano-service confetti (a service per entity) · the extraction driven by a diagram instead of a number · the "temporary" dual-write that outlives its author.

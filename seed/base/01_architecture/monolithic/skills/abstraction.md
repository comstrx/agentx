# Abstraction

The craft of compressing a system until features cost declarations — without ever crossing into obscurity.

- **The engine mindset:** every repeated shape is a machine waiting to be built. The first occurrence lives concrete; the second triggers extraction — and the extraction removes BOTH copies, leaving two declarations over one engine. Never extract on the first, never tolerate the third.
- **Name the seam before cutting it:** an abstraction begins as a name (`Scope`, `Ledger`, `Throttle`, `Saga`) that the domain would recognize — if the name needs a sentence, the boundary is wrong. The name decides the altitude: primitive nouns sink to the foundation, pattern nouns to the engine, business nouns stay in the domain.
- **An abstraction's altitude = the lowest layer where every consumer can reach it.** Extract downward to exactly that layer and no lower — a foundation helper serving one feature is premature; an engine behaviour re-implemented per feature is late.
- **Absorb the native world once:** runtime, framework, and vendor APIs are wrapped at the foundation/seam layer so upper code speaks the project's vocabulary — the wrap is where guarantees (timeouts, redaction, tenancy keys, escaping) are enforced for everyone, once.
- **The declare→materialize test:** a well-abstracted subsystem lets a new case arrive as data + a small declaration (fields, capabilities, a strategy) while the machinery materializes the rest. If a new case needs plumbing, the engine is missing a piece — grow the engine with exactly that piece, then re-declare.
- **Judge at the call site, not the implementation:** the measure of an abstraction is what its consumer's line looks like — one readable sentence with obvious parameters. An impressive engine with awkward call sites failed; iterate the surface from real usage backwards.
- **Uniform verbs across domains:** `get/set/has/make/parse/format/resolve` mean the same thing everywhere; parameter orders are consistent; behaviour is symmetric (`open/close`, `acquire/release`). Guessability is the compound interest of abstraction — every learned corner teaches the rest.
- **The two failure poles, patrolled equally:** under-abstraction shows as copies and shotgun edits (one rule, five addresses); over-abstraction shows as indirection with one implementation, config nothing sets, and layers whose only job is passing calls through. Both are defects; the rule of two is the referee.
- **Deterministic magic only:** derived behaviour (discovered maps, generated surfaces, convention-driven wiring) must be printable, inspectable, and fail-loud on the unknown key. Automation the team can dump and read is leverage; automation that surprises is a bug factory wearing a cape.
- **Composition beats parameters:** when an abstraction grows its fifth boolean/option, it is two abstractions fused — split along the option that changes behaviour shape, compose at the call site. Small orthogonal pieces outlive configurable monoliths.
- **Deletion is part of the craft:** an abstraction whose consumers dropped to one gets inlined back; a seam nothing swaps or fakes gets removed. The engine stays powerful because it is curated — pruning is the same skill as planting.
- The end state to defend: the domain layer reads like the business, the engine reads like a pattern catalog, the foundation reads like a standard library — and a stranger can tell which file belongs to which by its nouns alone.

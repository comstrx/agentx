# Offline

- **Offline is a mode the app is DESIGNED for, not an error it apologizes for:** airplane mode shows a working product — browsable content, the user's own world (orders, bookings, tickets, owned content) fully readable, actions queued with honest pending states. A blank screen behind a "no connection" toast is a rejected deliverable.
- **Reads: cache is the only source the UI knows.** Every screen renders from the persisted local cache instantly; the network refreshes the cache in the background (on focus, on reconnect, on interval where live matters) — the UI never awaits a fetch to paint; it awaits nothing.
- **Writes: the queue is the contract.** Offline mutations persist to a durable queue (id, timestamp, payload, idempotency key) and apply optimistically to the local view; on reconnect the queue replays IN ORDER against the server — the same idempotency keys the backend demands make replay safe by construction.
- **Conflicts resolve server-side, reconcile client-side:** the server is the arbiter (version checks, last-write rules, domain-specific merges — declared per resource); the client submits, receives the verdict, and reconciles its optimistic view — including showing the user when their offline change lost ("this booking was modified; review"). Silent overwrite in either direction is data loss with a UX.
- **Not everything queues — declare the split:** browsing actions, drafts, toggles, notes → queue freely; money movements and inventory-taking commitments (payment, booking confirmation) → require connectivity with an honest "needs connection to confirm" state — an offline "confirmed" that later fails is a broken promise the product made.
- **Pending state is a first-class UI vocabulary:** queued items marked visibly (syncing, pending, failed-will-retry, failed-needs-you), a way to inspect and cancel queued actions, and failure escalation to the user only when retry policy is exhausted — the user always knows what the app has promised on their behalf.
- **Staleness is labeled where it matters:** cached availability, prices, and balances carry their age when the domain's tolerance is short ("as of 2h ago") — presenting stale money-shaped data as fresh is a lie with a timestamp alibi.
- **Storage tiers by sensitivity and shape:** tokens in secure storage, the query cache in fast key-value, relational offline data (owned content, queues) in the on-device database — with size budgets, eviction for the cache tier, and NEVER eviction for the queue tier (a garbage-collected pending write is a lost user action).
- **Sync is observable in the field:** queue depth, replay success rate, conflict rate, cache hit ratio at cold start — shipped as telemetry; offline bugs reproduce in nobody's office, they diagnose by these numbers or not at all.
- Test offline as a scenario suite: cold-start offline · act-offline-then-reconnect · conflict on replay · kill-app-mid-queue · clock skew — run on device profiles, not just simulators; the offline promise is the app's hardest contract and gets suite coverage like one.

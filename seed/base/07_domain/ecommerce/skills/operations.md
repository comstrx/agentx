# Operations

Running the commerce chain in production — the craft under the contracts.

- **Stock as movements, not a number:** an inventory ledger (received, reserved, committed, released, returned) with the available count derived — or cached and maintained atomically with the movement; the two-step `read count, write count-1` is the oversell generator. High-contention SKUs (flash sales) take the lock/version path; the long tail rides optimistic checks.
- **The reservation sweeper is half of checkout:** reservations carry an expiry, an index serves the sweep, release is idempotent and batched — a crashed checkout must return its stock without a human; reservation age and release volume live on a dashboard because a stuck sweeper IS an outage, just a quiet one.
- **The coupon engine is constrained data + one validation pipeline:** scope (products/categories/vendors), window, usage caps (global + per-actor), stacking rules, minimums — validated server-side at placement in one pipeline that records WHICH rules passed; usage counting is atomic under the same key discipline as any counter. A coupon honored from the cart payload is a price the client wrote.
- **Pricing stages write receipts:** base → rules (seasonal/tier) → coupons → taxes — each stage a named unit appending its contribution to the order's recorded math; support reads why the total is 240, finance reconciles it, and a pricing bug is diffed stage by stage instead of re-derived from memory.
- **Checkout end to end under one idempotency key:** placement, payment intent, and confirmation webhooks all guard by the key — the double-click, the mobile retry, and the duplicate webhook converge on ONE order; the suite proves it by firing the duplicates deliberately.
- **Multi-vendor truth at capture:** per-vendor order groups with independent fulfillment states; commission and vendor-share ledger entries written at capture/settlement through the payment machinery; payouts drain vendor balances through the same port + idempotency + reconciliation rails as charges — the buyer sees one purchase, the books see the topology.
- **Returns/cancellations resolve policy from data:** the item's/vendor's policy declares legal source states, refund math (full/partial/fees), and the restock decision; execution is a state transition + ledger entries + (maybe) a stock movement — support triggers it, the machinery does it, improvisation does neither.
- **Fulfillment routes by capability strategy:** stock+shipping (carrier port, tracking events), instant-digital (entitlement + signed delivery), service-delivery (schedule + completion confirmation) — one order pipeline resolving `capability → strategy`; a new fulfillment shape is one strategy, never an if-ladder through the order service.
- **The order timeline is an event stream:** every transition, payment event, note, and notification appends — support's first screen is the timeline, disputes replay from it, and analytics read it; a `status` column alone answers nothing about the journey.
- Watch the money-shaped metrics: conversion through the funnel, payment success rate by provider, oversell incidents (target: structurally zero), reservation leakage, refund latency — commerce health is these numbers, not uptime alone.

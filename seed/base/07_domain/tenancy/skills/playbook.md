# Playbook

Running shared-schema multi-tenancy in production — the craft around the law.

- **The context is the single accessor:** middleware resolves domain + token → sets tenant/actor/panel into the request-scoped context → every layer reads from it — nothing else re-parses hosts or re-derives tenancy; long-lived workers reset it per request/job, guaranteed by the framework's lifecycle hooks.
- **The tenancy trait guards ALL THREE write moments, not just reads:** the global scope filters queries · `creating` stamps the tenant id when absent · `deleting`/`updating` VERIFY the row's tenant against the context and refuse (403) on mismatch — the third guard is the one implementations forget, and it is what stops a leaked id from becoming a cross-tenant write. The trait mounts flexibly: self-deactivates when the table lacks the scope column or no tenant is resolved, honors the model's opt-out list, and lets the scope column name be overridden per model — mountable everywhere, silent where inapplicable, fail-closed where applicable.
- **RLS wiring that actually holds:** the policy reads a transaction-local setting (`set_config(..., true)`), set inside the transaction by the connection layer; session-level SET leaks across pooled connections — the classic hole. Verify with a two-tenant probe query in the suite, connected exactly as production connects.
- **Per-plan and per-tenant limits ride the scope:** throttle keys, storage quotas, seat counts — all keyed by tenant, resolved from the tenant's plan; one tenant's abuse degrades that tenant only. Noisy-neighbor pressure (a tenant's report storm) isolates by queue fairness — per-tenant job batching or weighted queues, measured before invented.
- **Tenant-aware operations:** migrations run once (shared schema — its superpower); backfills chunk BY tenant (progress trackable, blast radius bounded); a data incident's first question is "which tenants" — design audit trails and backups to answer per-tenant, restore per-tenant where the stake demands it.
- **Custom domains as data:** a domains table (tenant, domain, verification state, TLS state) driving resolution + a provisioning saga (DNS verify → certificate → activate) through the provider port — a domain is a tenant asset with a lifecycle, not a config file entry.
- **Branding/config per tenant is data with defaults:** platform defaults ← tenant overrides, merged through one resolver, cached tenant-scoped — the same cascade shape as permissions; never per-tenant code, never per-tenant templates on disk.
- **Onboarding is a product path:** tenant row + owner user + seeded defaults (roles, permissions, settings) + subdomain live — one transaction-safe provisioning flow, idempotent, testable, fast enough to demo live.
- **Debugging across tenants:** support tooling impersonates through the audited escape with the actor's identity recorded — "log in as the customer" is a designed, logged capability, or it becomes an unlogged habit.

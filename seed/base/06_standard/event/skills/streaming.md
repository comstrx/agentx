# Streaming

Operating log-family brokers (Kafka/Redpanda) and stream consumers in production.

- **Partition count is the concurrency ceiling, set at birth:** consumers in a group ≤ partitions (extras idle); repartitioning later breaks key→partition mapping (per-key order across the boundary) — over-provision partitions at topic creation (cheap) rather than migrate under load (surgery).
- **The partition key is a design artifact:** the entity id whose events must order (order id, booking id, tenant+entity for balance) — a null/random key throws ordering away silently; a low-cardinality key (tenant id alone on a whale tenant) creates a hot partition that one consumer must drain alone. Review keys like schema.
- **Consumer groups, the operational contract:** one group per logical consumer (the mailer, the projector, the indexer) — scaling = adding members to the group; a new use case = a NEW group reading the same topic from its own offset, which is the whole point of the log.
- **Rebalances are the hidden tax:** every deploy/scale triggers one; long-running message handling stalls the group (max-poll deadlines kick members out mid-work) — keep per-message work short (heavy work → hand off to a job queue), use cooperative/incremental rebalancing where the client offers it, and make handlers safe against the redelivery a rebalance causes.
- **Commit offsets AFTER the effect, never before:** auto-commit-on-poll acknowledges work not yet done (crash = silent loss); commit after the handler's transaction — the resulting at-least-once duplicates are the idempotency layer's job, and that layer is mandatory, not optional.
- **Lag is THE health metric:** per-group, per-partition lag on dashboards with alerts — growing lag names its cause (slow handler, hot partition, dead member) before users do; zero lag forever on a busy topic means someone is committing without processing.
- **Retention and compaction are data design:** time/size retention for event streams (consumers must finish within the window — a consumer down longer than retention has LOST data: alert on that horizon); compacted topics for latest-state-per-key feeds (changelogs, config streams) — choose per topic, write it in the topic's declaration.
- **The DLQ pattern for streams:** after bounded in-consumer retries, publish the poison event + error context to a dead-letter TOPIC and commit past it — one bad event must never park a partition; the DLQ has an owner, a dashboard, and a replay-into-main path.
- **Replay is a rehearsed capability:** projections rebuild by resetting the group's offset (new group name = zero-risk parallel rebuild, swap when caught up); side-effecting consumers replay only behind their idempotency guards — the first replay happens in a drill, not an incident.
- **Schema evolution rides a registry or a convention:** versioned envelopes, additive-only payloads, consumers tolerant of unknown fields — a producer deploy must never require a same-moment consumer deploy; the compatibility check runs in CI, not in production.
- Local truth for tests: single-node Redpanda in the suite exercises real partitions/groups/offsets — mocking a broker proves the mock; the pathological tests (duplicate, reorder-across-keys, rebalance mid-batch, lag recovery) run against the real protocol.

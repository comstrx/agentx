# Engines

- **The escalation ladder is law: database full-text first, a dedicated engine only on measured need.** Every rung up buys capability and pays in ops (a cluster, a sync pipeline, a second source of staleness) — the swap is a driver file because the facade demanded it from day one; the DECISION is a measurement, never a mood.
- **Rung 1 — the database itself:** Postgres `tsvector` + GIN for full-text, `pg_trgm` for fuzzy/`ILIKE`, expression indexes for prefix lookups — zero new infrastructure, transactionally fresh, tenant-scoped by the same query discipline as everything else. It carries most products further than teams expect; leaving it requires a number (latency under load, relevance ceiling, facet cost).
- **Rung 2 — Meilisearch, the product-search sweet spot:** instant (<50ms) prefix/typo-tolerant search, faceting, sane defaults, single-binary ops — the house pick for catalog/storefront search where the experience is "type, see results now". Its limits are honest: single-node scale ceiling, simpler query algebra — hitting them is the signal for rung 3, not a workaround festival.
- **Rung 3 — Elasticsearch/OpenSearch, the analytical heavyweight:** arbitrary aggregations, complex query DSL, horizontal scale, mature per-locale analyzers — earned by facet/aggregation complexity or index size that Meilisearch measurably cannot serve. It charges rent: cluster sizing, shard design, JVM care, upgrade choreography — a team buys ES, it does not just install it.
- **Rung 4 — Vespa, the specialist:** giant-scale serving with ML-ranked/vector/hybrid retrieval, computation pushed to the data — the rung for semantic search and recommendation-shaped retrieval at serious scale. Choosing it is a platform decision with a team attached; it never sneaks in as "better ES".
- **Vector/semantic search is a capability, not a rung:** `pgvector` at rung 1, engine-native hybrid (ES/Vespa) above — the same ladder logic applies: start where the data lives, escalate on measurement; hybrid (keyword + vector, fused) beats either alone for product search and is designed as ONE ranked query, not two glued lists.
- **The contract every engine must honor behind the facade:** scoped queries (tenant baked at build) · declared searchable/filterable/sortable fields only · ids-out hydration through the primary store · async idempotent indexing · rebuild-from-scratch by one command — an engine that tempts the project to violate one of these (serving full documents, sync writes) is being used wrong, not being clever.
- **Relevance portability is a myth — plan for it:** analyzers, ranking, and typo behavior differ per engine; a rung change re-runs the golden query set (query → expected top results) as the acceptance gate — the suite, not nostalgia, says the swap held.
- Cost the staleness honestly per rung: rung 1 is transactional (zero lag) — every rung above introduces sync lag that the product must declare (seconds is fine for catalog, wrong for permissions) — a search feature whose staleness tolerance was never written down will surprise someone with it.

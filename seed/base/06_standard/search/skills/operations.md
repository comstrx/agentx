# Operations

Running search engines in production — the ops craft each rung of the ladder demands.

- **The sync pipeline is the system's weakest joint, monitor it first:** queue lag (writes → index), error rate on index jobs, and a scheduled count-drift check (source rows vs index docs, per scope) — silent index rot is found by customers otherwise; the drift check is a cron with an alert, not an intention.
- **Reindex without downtime, rehearsed:** build into a fresh index → alias/atomic swap → drop the old; chunked by keyset, resumable, rate-limited against the primary store. The rebuild command exists from day one and gets run in a drill — the first schema change that needs it must not be its first execution.
- **Zero-result queries are the product's backlog:** log them (with locale + filters), review on rhythm — they name missing synonyms, missing content, and broken analyzers better than any metric; a spike in zero-results after a deploy is a relevance regression alarm.
- **Meilisearch ops in practice:** single node = size RAM to the index (it is memory-hungry by design), snapshot/dump on schedule, watch indexing queue saturation under bulk loads — its simplicity is real, but "no cluster" means the vertical ceiling and the restore story are YOUR capacity plan.
- **Elasticsearch ops in practice:** shard count set at index birth (over-sharding wastes heap, under-sharding caps growth — size by data math, not defaults), ILM for time-shaped indices, JVM heap ≤ 50% of RAM, disk watermarks alarmed BEFORE read-only mode surprises writes, and upgrades walked minor-by-minor with snapshots taken — a red cluster teaches these in the worst classroom.
- **Postgres-as-search ops:** the GIN indexes join the same maintenance story as every index (bloat, reindex concurrently), `tsvector` columns maintained by trigger/generated column — and the moment search queries dominate the primary's load profile, that IS the measurement that funds rung 2.
- **Locale/analyzer changes are reindex events:** analyzers bake at index time — changing stemming/synonyms/normalization (the Arabic normalization set: hamza forms, teh-marbuta, diacritics) requires the rebuild path; test analyzer changes against the golden set + native-speaker queries in staging, never live.
- **Capacity tests use production-shaped data:** relevance and latency both change with corpus size and term distribution — a 1k-doc staging index proves nothing about the 10M-doc production behavior; load-test with a masked production snapshot before the launch that matters.
- **Security posture per engine:** engines hold a projection of scoped data — network-private always, authenticated always, and the projection excludes what permissions would hide (the index is queried by the app, but defense-in-depth says never index what no one may see).
- The engine dashboard a stranger can read: sync lag · query p95 · zero-result rate · index size/growth · per-scope doc counts vs source — five numbers that say "search is healthy" or name the sick part.

# Mysql

- **MySQL/InnoDB when the project inherits it or the team's ops story demands it** — competent, ubiquitous, operationally boring. The law here is knowing where it DIFFERS from Postgres and never porting assumptions blindly.
- **The clustered primary key is the storage layout:** InnoDB stores rows IN the primary key's B-tree — a random primary key (UUIDv4) fragments every insert. Use time-ordered ids (UUIDv7 stored as `BINARY(16)`, or an internal auto-increment with the public UUID as a unique secondary) — the choice is a write-throughput decision, not a style one.
- **Secondary indexes carry the PK:** every secondary index entry includes the primary key — a fat PK taxes every index on the table; another reason the PK stays compact and ordered.
- **Charset is a decision made once:** `utf8mb4` + a deliberate collation (`utf8mb4_0900_ai_ci`-era) on EVERYTHING — `utf8` is a 3-byte lie that corrupts emoji and rare scripts; mixed collations break joins with silent full scans.
- **What Postgres has that MySQL does not — design around, never emulate badly:** no partial indexes (use generated columns + index, or restructure) · no expression indexes pre-8.0-functional (functional indexes exist in 8.0+, know the version) · no RLS (isolation is application-scope only — the global scope discipline carries ALL the weight) · no transactional DDL (a failed migration leaves half-applied state: migrations must be small, ordered, and verified) · no `RETURNING` (know the two-step patterns).
- **What MySQL does differently, exploited:** online DDL (`ALGORITHM=INPLACE/INSTANT`) for many alterations — know which class the change falls into before running it on a big table; `INSERT … ON DUPLICATE KEY UPDATE` as the upsert; generated columns for derived/JSON-extracted indexing.
- **The nullable-scope unique, closed the MySQL way:** a virtual generated key — `tenant_key` as `COALESCE(tenant_id, 0)` (`virtualAs`) — carries the composite unique (`unique(tenant_key, slug)`); NULL-scoped platform rows collapse onto the sentinel and duplicates become impossible without `NULLS NOT DISTINCT`. The same move builds upsert identities over nullable FKs (`unique(provider_key, ref_id)`). Enum-shaped columns derive from the PHP enum — `enum('status', array_column(Status::cases(), 'value'))` — one source of truth; widening the set is a migration, which is the point.
- **Gap locks are the surprise:** under the default REPEATABLE READ, range queries in transactions take gap/next-key locks — deadlocks appear in shapes Postgres never shows. Keep transactions short, index the lookup that the write uses, and read deadlock traces (`SHOW ENGINE INNODB STATUS`) instead of guessing.
- **`ONLY_FULL_GROUP_BY` stays on** (the modern default) — a query that "worked" by picking arbitrary values from a group was a bug wearing a result set.
- **JSON exists but is weaker:** JSON columns query through path functions + generated-column indexes — heavy JSON querying is a signal the data wants columns or wants Postgres; decide, don't wrestle.
- **Replication defaults to async:** a read replica may serve stale reads — read-your-own-writes flows pin to the primary or use the write connection; semi-sync/group replication is an ops decision declared, never assumed.
- Observe with the engine's tools: slow query log + `performance_schema` + `EXPLAIN ANALYZE` (8.0.18+) — the tuning discipline is identical to Postgres even when the instruments differ.

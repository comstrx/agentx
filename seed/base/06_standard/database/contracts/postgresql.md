# Postgresql

- **PostgreSQL is the house default** — chosen for what the others lack: transactional DDL, RLS, partial/expression/covering indexes, `jsonb` with GIN, rich types, `NULLS NOT DISTINCT`, `SKIP LOCKED`. Use these deliberately; treating Postgres as generic SQL wastes the reason it was picked.
- **Types are the schema's vocabulary:** `timestamptz` always (never naive timestamps), `numeric` never for money (integer minor units), `text` over sized varchar unless the bound is a real rule, native arrays/`jsonb` for genuinely open shapes, domain-checked columns via `CHECK` — the richest type that tells the truth.
- **`jsonb` discipline:** GIN for containment queries (`@>`), an expression index `((attributes->>'k'))` for one hot key — cheaper than whole-column GIN; a `jsonb` column whose keys every query touches is a table dodging a migration.
- **The index arsenal, used precisely:** partial (`WHERE deleted_at IS NULL`, hot statuses) · covering (`INCLUDE` for index-only list scans) · expression (lowercase lookups, jsonb keys) · GIN (jsonb, arrays, trigram search) · BRIN (huge append-only time-series). Every migration adding one names the query it serves.
- **Transaction-local settings only:** `set_config(key, value, true)` inside the transaction — session `SET` leaks across pooled connections; this is the RLS wiring rule and the general law both.
- **RLS as defense-in-depth:** `ENABLE` + `FORCE ROW LEVEL SECURITY` on scope-owned tables, policies reading the transaction-local setting, the app connecting as a **non-owner** role (owners bypass RLS) — migrations run as owner, the app never does.
- **The NULL-distinct trap closed explicitly:** unique indexes treat NULLs as distinct — nullable-scope uniques need `UNIQUE … NULLS NOT DISTINCT` (PG15+) or a partial unique `WHERE scope IS NULL`.
- **Concurrency instruments:** `SELECT … FOR UPDATE` on contended rows, `SKIP LOCKED` for queue-shaped tables, advisory locks for app-level mutexes, statement timeouts so a stuck query errors instead of outages — each a named tool, reached for by shape.
- **MVCC has a bill:** dead tuples from update-heavy tables need autovacuum tuned per table (hot tables get aggressive settings); long-running transactions block vacuum platform-wide — kill the idle-in-transaction, chunk the bulk work.
- **Migrations exploit transactional DDL:** schema changes commit atomically or not at all — but `CREATE INDEX CONCURRENTLY` (the production default on big tables) cannot run in a transaction; the migration runner must know the difference.
- **Extensions are part of the platform:** `pg_trgm` (fuzzy search), `pgcrypto`/`uuid` needs, closure-friendly CTEs, `pg_stat_statements` (always on — it is the tuning work queue). An extension the project relies on is declared in migrations, never hand-installed.
- Observe it as a system: `pg_stat_statements` for the worst queries, bloat and replication lag on dashboards, connection counts against `max_connections` math — Postgres degrades loudly only if someone is listening.

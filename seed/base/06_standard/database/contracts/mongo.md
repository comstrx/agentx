# Mongo

- **MongoDB only when the domain is genuinely document-shaped:** deeply nested aggregates read/written whole, schema variance that is real (not laziness), horizontal write scale as a proven need. A relational domain forced into documents pays with hand-rolled joins and application-enforced integrity — the default answer remains the relational engine.
- **Schema-on-write discipline, always:** collection validators (JSON Schema) + typed models at the application boundary — "schemaless" is a capability for evolution, never an excuse; a collection whose documents disagree about shapes is a parser farm, not a database.
- **The one design decision: embed vs reference.** Embed what is read together, owned together, and bounded (an order's items); reference what is shared, unbounded, or independently queried (the user on an order). The unbounded-array embed (comments growing forever inside a post) is THE classic corruption — bounded embeds, referenced collections past the bound.
- **Ids follow the house law:** time-ordered ids (`ObjectId` already is; UUIDv7 where the platform standardizes) — and every scope-owned document carries its scope field (`tenant_id`), indexed first, exactly like every other store.
- **Indexes are B-trees with the same disciplines:** compound indexes follow equality→sort→range ordering (ESR), covered queries for hot lists, partial indexes exist here too, multikey (array) indexes have fan-out costs — `explain()` is the truth, the ODM is the suspect.
- **Transactions exist and are a smell:** multi-document ACID works (replica sets), but a flow needing them constantly is a relational domain in disguise — the aggregate should have been one document, or the store should have been Postgres. Single-document atomicity (`findOneAndUpdate` with operators) is the native idiom; reach for it first.
- **The aggregation pipeline is the query engine:** match early (indexes work only on the leading `$match`), project narrow, `$lookup` sparingly (a pipeline of lookups is a join-shaped domain), and treat pipelines as versioned code — named, tested, never console-crafted into production.
- **Concurrency without row locks:** optimistic versioning (a `version` field in the update filter) guards read-modify-write; atomic update operators (`$inc`, `$push` with `$slice`) mutate in place without the round-trip — the wallet-style balance UPDATE race exists here too and is guarded the same way.
- **Consistency is a per-query decision:** write concern `majority` for anything that must survive an election; read concern/preference chosen per flow — reading your own write from a secondary is the classic Monday bug; money-shaped flows pin to primary with majority both ways.
- **Growth mechanics differ:** documents that grow rewrite; hot arrays fragment — size the document for its lifetime shape. TTL indexes handle expiring data natively (sessions, intents) — a cron deleting old rows is built-in here; use it.
- Operate it like the grown-up it is: replica set always (even "small" production), oplog window monitored, backups tested by restore, `currentOp`/profiler for the slow — Mongo fails operationally before it fails logically.

# Choice

Picking the store by the differences that decide — never by fashion, résumé, or inertia.

- **The default is PostgreSQL, and the burden of proof is on leaving it:** transactional DDL, RLS, partial/expression/covering indexes, `jsonb`, `SKIP LOCKED`, `NULLS NOT DISTINCT` — the feature set that this stack's laws (tenancy defense-in-depth, queue tables, nullable-scope uniques) are literally built on. A choice away from Postgres must name which of these it abandons and what compensates.
- **MySQL earns the seat by circumstance, not capability:** an inherited system, a team whose ops muscle is MySQL, an ecosystem constraint. It is not worse at being a database — it is worse at THIS stack's specific tricks (no RLS, no partial indexes, no transactional DDL). Choosing it consciously means the application-layer scope discipline carries isolation alone, and migrations get the extra care half-applied DDL demands.
- **The engine-difference table that actually decides:** clustered PK (MySQL: id design is a write-throughput decision) vs heap (PG: vacuum is the bill) · MVCC bloat + autovacuum (PG) vs gap-lock deadlocks (MySQL) — every engine charges for concurrency somewhere; know WHERE before the incident does · replication: both default async — read-your-own-writes is an application pattern on either.
- **Mongo is a shape decision, not a scale decision:** choose it when aggregates are genuinely document-shaped and read whole; never because "it scales" (Postgres partitions and replicates further than most products ever need) or because migrations feel like friction (schema evolution without discipline is corruption on a delay timer).
- **Redis is a data-structure server, not a database:** the source of truth for nothing the business cannot lose — cache, locks, counters, queues, presence, rate limits: yes; the only copy of an order: never. Durability (AOF/RDB) narrows the loss window; it does not make Redis a system of record.
- **Polyglot persistence is paid for per store:** every additional engine costs backups, monitoring, upgrade cycles, a mental model, and a failure mode — a second store earns its place by a measured need the primary provably cannot serve (search → the search node's ladder; analytics → columnar; queues → the broker decision), never by preference.
- **The migration cost is part of the choice:** moving OFF a store later costs a dual-write/backfill/cutover project — so the cheap reversible experiment is a schema inside Postgres (jsonb, partitions) before it is a new engine beside it.
- **Ask the five questions, write the answers down:** what are the top five queries? what must be transactionally consistent? what is the isolation/tenancy story? what does ops already run well? what is the growth shape (rows, writes/sec, retention)? A store chosen without written answers was chosen by mood.
- Revisit with numbers only: the store is re-evaluated when a measured limit approaches (p95 under load, storage math, vacuum/replication strain) — migrating stores on vibes is how a year disappears.

# Gateways

Driving real payment gateways — the craft between the port and the provider's chaos.

- **Intent-based flows are the modern shape:** create the provider intent server-side against the local pending intent → the client confirms with the provider's SDK (card fields, 3DS challenge, wallet sheet) → the webhook finalizes. The client never sees amounts as authority, never talks to your API about success — the webhook is the truth channel, the redirect/return is UX; SCA/3DS means ANY charge may detour through a challenge, so every flow is built redirect-tolerant.
- **Integration surface chosen by PCI reality:** hosted checkout (provider page — smallest compliance surface, least control) · embedded elements/fields (provider-owned inputs in your UI — the usual sweet spot) · native mobile sheets (through the port's mobile drivers) — raw card APIs demand a compliance program; choosing them is a business decision with an auditor, not an engineering shortcut.
- **Auth-then-capture is a product lever:** authorize at commitment, capture at fulfillment (ship/check-in/delivery) — the booking-shaped domains' natural fit; authorizations EXPIRE (days, per scheme/provider) so the sweeper re-authorizes or releases before the window closes, and partial captures reconcile against the authorized remainder.
- **Idempotency speaks the provider's dialect too:** every provider call carries the provider's idempotency mechanism keyed from the LOCAL intent — a network timeout on `create charge` is retried with the same key, and the sweeper resolves "did it land?" by querying with the local reference, never by charging again on doubt.
- **Multi-gateway is routing config behind the port:** per-currency, per-region, per-method, per-tenant routing tables select the driver; failover to a second gateway happens ONLY on provider-down class errors (never on decline — a decline retried elsewhere is card-testing behavior that gets the platform flagged). Fees and settlement currencies ride the routing decision — cheapest-capable wins by data.
- **Declines are data, not errors:** map provider decline codes at the port into the project's taxonomy (insufficient/do-not-retry/retriable-later/fraud-block) — the UX, the retry policy, and the dunning schedule branch on the class; raw provider strings reaching a user or a log-based alert are a leak.
- **Payment methods are capabilities, declared:** cards, wallets (Apple/Google Pay), bank redirects, cash-on-delivery, regional methods — each a method entry the type/tenant declares, each with its own state nuances (bank redirects have no instant answer; COD confirms at fulfillment) composed onto the same intent machine.
- **Fees, payouts, and settlement are ledger topology at the gateway seam:** provider fees ledger at capture from the webhook's actual amounts (never assumed from rate cards), settlement currency conversions record both sides + rate, payout schedules respect the provider's holds — finance reconciles the provider's reports against these entries on rhythm.
- **The sandbox matrix is the suite:** per driver — happy card, every decline class, 3DS challenge success/abandon, webhook duplicate + out-of-order, timeout-then-succeeded, partial capture, refund + dispute — providers ship test triggers for each; the matrix runs green before a driver ships and after every provider SDK bump.
- Fraud posture is layered and honest: provider-side tools (radar-shaped) first, platform velocity checks (per-actor/per-card attempts) second, manual review queues for the flagged — the platform never stores enough card data to "build its own" and should not want to.

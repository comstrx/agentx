# Database

- **UUIDv7 primary keys on every NEW schema; ids are `string` in every signature.** UUID means UUID *columns* everywhere: `uuid('id')->primary()` (never `id()`/`bigIncrements`), `foreignUuid()`/`uuid()` (never `foreignId()`), and **`uuidMorphs()`/`nullableUuidMorphs()`** (never `morphs()` — a bigint morph id cannot hold a UUID). Convert every framework scaffold migration that ships bigint (`personal_access_tokens`, `jobs`, `cache`, `sessions`, `users`) before it ships — a bigint id against UUID models is latent corruption, not a style nit. **An EXISTING project's established key type is its law** — a numeric-id codebase stays numeric consistently (`whereNumber` constraints, `int` signatures throughout); read the migrations before writing one, and never mix key types in one schema.
- **The engine is read from `config/database.php` before any engine-specific move — the schema law must hold on BOTH Postgres and MySQL:** on Postgres reach for its arsenal (RLS, partial/expression indexes, `NULLS NOT DISTINCT`, jsonb+GIN); on MySQL compensate deliberately — no RLS means the global scope carries isolation ALONE (raise the write-path guards accordingly), no partial indexes means generated columns + index, no transactional DDL means small verified migrations, and the clustered PK makes time-ordered ids a write-throughput requirement, not a preference. An agent porting Postgres assumptions onto MySQL unread is writing latent corruption.
- **`tenant_id`** (UUID, indexed, FK) on every tenant-owned table. **Every business unique includes `tenant_id`** — `users` is `unique(email, tenant_id)`, NEVER `unique(email)` alone; apply the same to phone/username. Composite uniques and hot indexes **lead with `tenant_id`**.
- **The NULL-distinct trap:** Postgres treats NULLs as distinct in unique indexes, so nullable-`tenant_id` (platform-level) rows escape `unique(x, tenant_id)`. Close it explicitly: `UNIQUE … NULLS NOT DISTINCT` (PG15+), or a partial unique `WHERE tenant_id IS NULL`, or upsert-only authoring. A duplicate platform row in a settings/permission table is a correctness bug.
- **RLS is defense-in-depth, the Eloquent global scope is primary:** transaction-local `set_config('app.tenant_id', ?, true)` — never session `SET`; the app connects as a **non-owner** role; tenant tables get `FORCE ROW LEVEL SECURITY`. Keep the small explicit list of platform tables that are deliberately unscoped.
- **Migrations: central, reversible, additive-first.** No destructive drop in the same release as code still reading the column; backfill → switch reads → drop later. Every index change names the query it serves.
- **Money is integer minor units in a double-entry ledger — never floats.** Same law as key types: an EXISTING project's established money representation is its law — a `decimal(12,2)`-through-one-rounding-helper codebase stays that way consistently; never mix representations in one schema. Time is UTC. Closed sets are PHP enums cast on the model via the `casts()` method. Soft-delete where the domain needs it, not by default.
- Tables plural snake_case; FKs `<singular>_id`; pivots alphabetical singular pair unless a domain name is clearer.
- Query discipline: parameterized always, keyset pagination on anything that grows, `whereUuid` route constraints, no unbounded `IN` lists, chunked iteration for bulk work.

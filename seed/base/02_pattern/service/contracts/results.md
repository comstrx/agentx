# Results

- **A use case answers with a typed result, never a shrug:** success carries the domain outcome (the entity, the receipt, the transition); failure carries a machine-readable reason the surface can act on — `{ ok, data | failure }`-shaped in spirit, expressed in each language's native result idiom.
- **Three failure families, never conflated:** validation (the input is malformed — the boundary's job, rarely reaches the service) · business refusal (the input is fine, the domain says no: insufficient balance, illegal transition, out of stock) · system failure (the world broke: provider down, deadlock, timeout). Each family has its own channel, status mapping, and retry semantics — a business refusal wrapped in a generic exception becomes a 500 that lies.
- **Business refusals are values, not exceptions:** expected domain outcomes ("no seats left") return as named refusal variants the caller matches on — exceptions/panics are reserved for the system family, where unwinding to the edge is the correct move; control flow by catching business exceptions is a `goto` with a stack trace.
- **Every refusal names itself stably:** a machine key (`insufficient_balance`, `hold_expired`) that survives refactors, maps to a status + localized message at the presentation layer, and appears in the API contract — clients branch on the key; the human message is decoration that may change freely.
- **Partial success is a designed shape, not an accident:** bulk operations return per-item outcomes (succeeded, refused-with-key, failed) — an all-or-nothing claim over a loop that half-ran is corruption reporting; if the domain demands atomicity, the transaction provides it and the result says so.
- **Results carry receipts for the expensive:** money movements return the ledger references, saga starts return the intent id + its state, async acceptances return what to poll/subscribe — "ok" without a handle to what happened forces the caller to go digging.
- **The mapping table lives at the edge, once:** refusal key → HTTP status/exit code/UI behavior in ONE translator per surface — services never know about status codes; surfaces never invent per-endpoint mappings; adding a refusal updates the table, not forty call sites.
- **Never leak the system family's guts:** provider errors, SQL states, and stack traces convert to safe system-failure results at the port/edge with the details logged under the correlation id — the caller learns "retryable or not", the log knows the rest.
- Uncertainty is its own outcome: a timeout against a money-moving provider is neither success nor failure — the result says `pending` with the intent reference, and the sweeper resolves the truth; reporting failure on doubt double-charges when the doubt was wrong.

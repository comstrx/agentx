# Lifecycle

Persistence hooks — the engine's moments around every write, used with surgical intent.

- **The hook ladder around a write:** before-create / before-update / before-delete (mutate or veto the incoming data) and after-created / after-updated / after-deleted (react to the committed fact) — implemented ONCE in the repository/model engine, invoked uniformly; a concrete declares only the hooks where it genuinely differs.
- **Before-hooks own the stamps:** scope id (tenant), time-ordered id, actor attribution, defaults, derived columns (slugs, normalized forms) — stamped centrally so no write path can forget them; a controller or service hand-setting `tenant_id` is a leak of the engine's job.
- **Before-hooks guard the immutables:** columns that never change after creation (type, scope, ledger references) are stripped/rejected in the update hook — an immutability rule enforced in one place beats a code-review reminder in twenty.
- **After-hooks fire the consequences, post-commit:** cache invalidation (tags/versions), search-index queueing, counter maintenance, domain-event emission — always after the transaction commits; an after-hook doing consequences inside the transaction couples the write's success to the cache's mood.
- **Delete hooks decide the cascade policy explicitly:** what the domain owns dies with it (an order's items), what it references survives (the product on an order snapshot), what history demands soft-deletes — declared per relation in the engine's vocabulary, never left to the database's `ON DELETE` alone (defense-in-depth: both agree).
- **Hooks are thin dispatchers, not business venues:** a hook body is a few pipeline calls (stamp, flush, enqueue, emit) — business logic discovering it lives in a hook migrates to the service/use case; the hook reacts to writes, it does not decide them.
- **Ordering and reentrancy are designed:** hooks fire in a declared order; a hook triggering another write (counter update) must not recurse into its own family — the engine guards reentrancy once (a hook-depth check, an internal-write flag), never per concrete.
- **Bulk operations choose their hook contract:** engine-level bulk writes (upserts, mass updates) may bypass per-row hooks for speed — the bypass is EXPLICIT at the call site, and the caller owns the skipped consequences (invalidation, indexing) in the same change; a silent hook bypass is a stale-cache generator.
- **Failure semantics per side:** a before-hook failing vetoes the write (fail-closed, the error surfaces); an after-hook failing must NOT un-commit reality — after-hook work is idempotent and retryable (queued where it matters), logged loudly where it is best-effort.
- Test hooks through the engine's surface: create/update/delete a fixture and assert the stamps, the guards, the fired consequences — plus one test proving the bulk path's explicit contract; hooks are the highest-leverage code in the write path and earn suite coverage accordingly.

# Events

- **A domain event is a past-tense fact the business would say out loud:** `booking.confirmed`, `wallet.debited`, `enrollment.expired` — named in the ubiquitous language, meaningful to a domain expert, worthless as a technical ping (`row.updated` is not a domain event, it is a trigger with ambitions).
- **Events record decisions, not intentions:** emitted when an aggregate COMMITS a meaningful change — after the invariants held and the transaction succeeded; an event describing uncommitted state is a lie under rollback, and an event emitted "so someone will do the thing" is a command in a costume.
- **The decision stays clean; the consequences stay pluggable:** the aggregate/service decides and emits; policies/listeners react ("when booking confirmed → reserve stock, notify vendor") — consequences added, removed, and reordered without ever touching the deciding code. Extra lines inside the confirm method for each new consequence is the coupling the pattern exists to kill.
- **One event, one meaning, forever:** the payload carries identity + the decision's data (what changed, from what, by whom, when) — consumers must never need to query "what did this actually mean". Renaming or repurposing an event is a breaking change to every consumer's understanding; new meaning = new event.
- **Granularity follows the business sentence:** one meaningful fact per decision — not a spray of field-level changes (`name_changed`, `status_changed` ×5 per save), not a mega-event smuggling the whole aggregate. If the domain expert would say it as one sentence, it is one event.
- **Internal first, exported deliberately:** domain events serve the module/context that owns them; the subset OTHER contexts may consume is a published contract (versioned, additive-only, translated at the border) — exposing every internal event as public API freezes the domain's ability to refactor itself.
- **Policies are named business rules, not glue:** each listener/policy carries a domain name (`ReleaseExpiredHolds`, `RewardFirstPurchase`) and reads as the rule it implements — anonymous closures reacting to events accumulate into a system nobody can enumerate; the policy catalog IS part of the domain model.
- **Time-triggered facts are events too:** expiry, deadline breach, window close — made explicit by sweepers that detect the condition and emit the event (`hold.expired`), so time-driven behavior rides the same policy machinery as action-driven behavior; a cron mutating state directly bypasses the domain's own vocabulary.
- **The event trail is the aggregate's biography:** persisted domain events (or the outbox trail) let support, audit, and debugging replay WHY the state is what it is — this is the pragmatic slice of event-sourcing kept (the trail), without the ceremony not needed (state still lives in tables).
- Test through events: a use-case test asserts state AND emitted events — the events are the observable decisions; a decision that emits nothing is invisible to the rest of the system and probably to the test too.

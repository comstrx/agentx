# Surface

The app's declared shape — tabs, screens, and what works without a network; the map every feature lands on.

- **Four tabs, one modal layer:** `Home` (tenant-branded discovery: featured, categories, continue-where-you-left) · `Search` (type-aware search + facets from the tenant's capability set) · `Bookings` (the user's world: upcoming/past orders and bookings, tickets, enrolled content) · `Account` (profile, wallet, payment methods, notifications, settings, support). Checkout, item detail, and pickers ride the modal/stack layer over any tab — the tab set is fixed; features compose into it, never add to it.
- **Every screen is a typed route in ONE map:** params typed, deep links and push notifications resolve through the same map with the parent stack reconstructed — `Bookings > BookingDetail > Voucher` from a cold push start, back button correct; a screen reachable only by one path is a screen half-integrated.
- **The offline contract per tab, declared:** `Bookings` = fully offline (the user's own world persists on device — vouchers, QR codes, tickets, enrolled content metadata render in airplane mode at the arrival gate, which is THE app's moment of truth) · `Home`/`Search` = cache-first browse with honest staleness · checkout commit steps = online-only with the designed "needs connection" state — this split is the product's offline promise; violating it in either direction (blocking bookings on network, faking offline checkout) is a contract break.
- **The archetype pickers are native composites:** calendar range (date-range types), session/seat sheets (timed-slot), quantity steppers + cart (stock), requirement forms (gigs), document capture with the camera pipeline (applications) — one picker family keyed by the type lookup, gesture-first, each a bottom-sheet flow that never leaves the item's context.
- **Tenant branding applies at runtime:** the brand payload themes the token system on app start per resolved tenant — one binary serves every tenant's app-in-the-browser links; white-label per-tenant store builds consume the SAME payload at build time, a packaging difference, never a code fork.
- **Push categories are product surface:** booking transitions (confirmed, reminder, needs-action), payment outcomes, messages, offers — each a category the user controls in Account, each deep-linking to its exact screen, offers ALWAYS separable from transactional (store policy and human decency both).
- **Identity on device:** tenant-bound tokens in secure storage, biometric unlock guarding the wallet and payment actions, session refresh silent — the API's tenant rules mirrored exactly; multi-account switching only if the product declares it.
- **Media discipline:** item galleries render CDN-sized variants with cache; the user's uploads (reviews, requirement documents) go through the on-device compress → resumable background upload pipeline — originals never re-upload, galleries never decode full-size.
- What "in the pocket" means as acceptance: the arrival-gate scenario (airplane mode, open voucher, scan QR) · the push-to-screen scenario (cold start from a booking-confirmed notification into the right detail) · the interrupted-checkout scenario (background mid-payment, return, state truthful) — all three pass on a mid-range Android before any release.

# Journey

The native booking funnel — the craft of making the commit path feel first-party in the hand.

- **Selection is gesture-native per archetype:** calendars swipe months and drag ranges, slot sheets scroll with haptic detents on selection, seat maps pinch-zoom, quantity steppers spring — the pickers are where the app must beat the mobile web, and they are built on the animation/gesture rails (worklet-driven), never on JS-thread timers.
- **The funnel survives the OS:** every step persists its state (typed route params + a draft record) — a phone call mid-checkout, a backgrounded app killed for memory, a payment sheet detour: return restores the exact step with selections intact; a funnel that restarts from Home after an interruption is a conversion funeral.
- **Payment goes through the native rails:** the payment port's mobile drivers present platform sheets (Apple/Google Pay) and SDK card fields — the app never renders raw card inputs of its own; 3DS/redirect detours open in the in-app browser and return by deep link into the SAME funnel step, state intact.
- **The commit step is online-only and honest about it:** connectivity checked at step entry, the "needs connection to confirm" state designed (retry on reconnect offered, selections held) — and placement carries the idempotency key from review-step entry so retries, double-taps, and reconnect races converge on one order.
- **Post-commit, push IS the confirmation UX:** the processing screen subscribes to the order's state (socket/poll) AND the confirmed push lands even if the user left — tapping it deep-links into the booking detail with the voucher ready; the user learns to trust that closing the app never loses a booking, which is the retention feature.
- **`Bookings` sync is the offline promise kept:** on every confirmation and on app focus, the booking's full offline packet (voucher, QR, dates, policy, tenant contacts) persists to the on-device store — the arrival-gate scenario (airplane mode, gate agent, QR scan) is rehearsed as a release check, not hoped for.
- **Needs-action states are push + badge + inline:** application types (visa documents), gig requirements, and payment retries surface as actionable items in `Bookings` with the deadline visible — the app's job is that no booking dies of user silence the product never asked to break.
- **Cancellation quotes before it commits:** the policy math (refund amount, window countdown) renders BEFORE the confirm — computed server-side, displayed verbatim; the refund shown is the ledger's number or the screen is lying.
- **Reviews ride fulfillment:** the review prompt arrives after the fulfillment transition (checked-out, delivered, course-completed) via the same push rails, deep-links into a one-screen review with the media pipeline for photos — verified-purchase linkage automatic because the entry point IS the booking.
- Measure the native funnel like the web one: per-step drop-off, picker abandonment, payment-sheet vs card-field completion rates, push-open-to-booking-detail latency, offline-voucher open counts — the numbers that prove the app earns its install over the site.

# Funnel

Composing fourteen types' purchase journeys onto one checkout spine — the site's hardest craft.

- **One spine, archetype steps composed on:** every funnel ends in the same commit sequence (review → idempotent placement → payment → webhook-confirmed state) — what differs per archetype is the SELECTION step before it: date-range pickers (calendar + guests), slot/seat pickers (sessions + capacity), carts (stock + quantities), instant (straight to commit), requirement forms (gigs), enrollment joins, document uploads (applications). Each selection step is one composed component keyed by the type's archetype from the lookup — a per-type checkout page tree is the fork that kills the multi-type thesis.
- **Availability UX is honest by design:** browse shows cached availability with its age where the domain's tolerance is short; the commit step re-verifies LIVE and the UI treats "just became unavailable" as a designed state (alternatives offered, dates nudged) — not an error toast; overselling apologies are a backend impossibility, so the frontend's job is graceful truth.
- **The selection state is URL-first:** dates, guests, slot, quantity ride searchParams through the funnel — shareable, refresh-safe, restorable from a WhatsApp link (how this market actually shares); losing a funnel to a refresh is a conversion bug, not a state bug.
- **Placement is idempotent from the client's side too:** the placement call carries the idempotency key generated at review-step entry — a double-tap, a back-button resubmit, or a flaky network converge on ONE order; the client renders whatever state the key's order already reached.
- **Payment states render the saga truthfully:** `processing` is a real screen with push/poll updates (the webhook drives the transition — the redirect return is UX, never the verdict); 3DS challenges are an expected detour; a stuck saga shows "still confirming" with support escalation — a spinner that lies times out into a support ticket AND a lost customer.
- **Multi-leg journeys (travels: package + visa assistance) render as staged commitments:** each leg's state visible, the order timeline showing which leg is confirmed/processing/pending-documents — one payment, staged fulfillment, zero pretending it is instant.
- **Guest checkout is the default posture:** account creation rides the confirmation (the booking IS the signup incentive), never gates the funnel entry; returning identification by email + OTP-shaped verification — every mandatory field before the commit step is measured against its drop-off cost.
- **The account area closes the loop:** orders/bookings render their state machines live (upcoming, needs-action for applications, cancellable within policy windows shown as countdowns), cancellation flows quote the policy's math BEFORE confirming — the refund the user expects is the refund the ledger writes.
- **Conversion instrumentation is funnel-native:** step entry/exit events per archetype, abandonment points, availability-refusal rates, payment-failure classes — the funnel is tuned from these numbers per type; a redesign without step data is taste, not optimization.
- Performance is a funnel feature: selection steps prefetch the next step's data on intent, the payment SDK lazy-loads at the payment step only, and the whole commit path stays interactive on mid-range mobile — every 100ms on the money path is measured revenue.

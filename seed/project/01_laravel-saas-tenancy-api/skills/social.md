# Social

The engagement suite — any model gains its full social surface by mounting one trait; the project-specific DNA subsystem.

- **One morph table per engagement kind, never a unified blob:** `views` · `likes` · `favorites` · `comments` · `replies` · `reviews` · `reports` · `shares` · `files` · `logs` · `notifications` — each polymorphic on `(engageable_type, engageable_id)` + `tenant_id` + `user_id` (the actor), each indexed `(tenant_id, engageable_type, engageable_id)`, each carrying exactly its own fields (`reviews.rating`, `reports.reason`, `files` path/mime/size + `kind` for image/qrcode).
- **One trait per table, one facade for the common set:** `Dna/Social/` holds `HasLikes`, `HasViews`, `HasComments`, `HasReviews`, `HasFavorites`, `HasReports`, `HasFiles`, `HasLogs`, `HasNotifications` — plus `HasSocial` composing the usual bundle; a model mounts exactly what it needs and that IS the whole integration: relations, scopes, counters, endpoints, and permission gates arrive with the mount.
- **`likes` is ONE toggle table with a boolean, not two tables:** a row per `(tenant_id, likeable_type, likeable_id, user_id)` with `like` true/false — like and dislike are mutually exclusive by construction; toggling flips the boolean and adjusts BOTH counters atomically; there is no `dislikes` table and never will be.
- **Presence toggles are unique rows:** `views` and `favorites` = one row per actor per target (`unique(tenant_id, *_type, *_id, user_id)`) — the toggle endpoint upserts/deletes; a duplicate-row count bug is structurally impossible.
- **Counters are denormalized and write-path-maintained:** `views`, `likes`, `dislikes`, `comments_count`, `rating_avg` live as columns on the engageable, adjusted atomically WITH the morph write (guarded by a `hasColumn` check so mounting a counter is opt-in per model) — recounting on read is forbidden; a drifted counter has a scheduled reconciler, not a COUNT(*) in the list query.
- **Moderation rides the same rows:** comments/reviews carry a status the transition machinery owns (pending → approved/rejected where the tenant enables moderation), `reports` feed a moderation queue with the reported morph target linked — the tenant's moderation toggle is a permission-cascade setting, not a code branch.
- **Engagement actions gate through the permission ladder:** `allow_comments`, `allow_reviews`-shaped cross-cutting flags resolve through the cascade per tenant/entity/item — a tenant disabling reviews for one product line is an entity-scope row, and the trait's endpoints answer 403 from the same verdict the panel faded.
- **Fan-out is queued, delivery is layered:** `notifications` + `notification_user` pivot fan out by bulk insert in a job; realtime badges broadcast immediately over the socket lane while mail digests queue — the same event feeds both lanes; nothing fans out inline in the request.
- **Reviews earn extra rules:** one review per actor per fulfilled order/booking (verified-purchase linkage), rating bounds enforced at the boundary, `rating_avg` recomputed from the write path with the count — a review without a fulfillment reference is unverified by design and marked so.
- Recommendation queries ride the morphs + locations closure: "users who favorited X", "top-rated in this city" resolve from the engagement tables joined through the closure — no per-pair relationship tables, no analytics detour for the product's own social proof.

# Checkout

The order funnel — preview → commit → pay — the money pipeline this product lives or dies by.

- **The pipeline order is law:** provider live-guard (OUTSIDE the transaction, fail-closed) → `dbTransaction(` identity/verification gate → precondition tables → discount resolution → totals finalization → commit-by-capability → secret-key generation `)` → post-commit consequences (invoice mail `afterCommit`, best-effort, caught + logged) → the payment leg. Validation never hides inside deeper steps; money math never runs outside the transaction; preview runs the SAME preconditions and totals as commit — a preview that lies is a support ticket factory.
- **Preconditions are match-tables returning `[field => Msg]`:** one `match ( true )` ladder per concern — catalog rules, quantity bounds, occupancy/stay fits, availability, then actor/catalog/tenant/category permission gates — first violation names the failing FIELD with a catalog Msg and the caller throws it as a 422. Declarative, exhaustive, testable row-by-row; an imperative if-cascade is the same table written illegibly.
- **Commit resolves by capability, never type:** `stockable` → conditional decrement (`where stock >= qty` in the UPDATE itself — no read-modify-write); availability/capacity-tracked → `lockForUpdate` the item row, then re-check per-night under the lock; default → plain commit. Adding an archetype adds a commit strategy, not an if.
- **Availability has ONE semantic, two compilations:** expressive PHP for the single item (calendar rows: closed windows, permit windows, capacity overrides, weekday bitmask) and compiled SQL for the search surface (leaf availability OR children-rollup for parent/room shapes, occupancy predicates included) — they answer identically by contract; changing one alone is a correctness bug the suite must catch with a paired test.
- **Provider-backed items add the live leg:** availability + price re-checked live through the port at preview AND commit — provider error refuses (UNAVAILABLE), never optimism; live cost above the local price refuses as CONFLICT — repricing is a human/sync decision, never checkout's.
- **The order row is a snapshot:** unit price + rate-plan id, currency + exchange rate, tax, penalty/deposit percents, cancel/refund windows (`allow_*` flags + `*_before` timestamps stamped from the policy at commit) — later policy edits never re-price history; disputes replay from the row, not from "what the policy says now".
- **Discounts stack through one resolver with a cap:** offer → coupon → level, each asking its own engine; non-stackable collisions resolve better-for-client; the tenant's cap percent trims in declared priority order; the full asked/applied breakdown persists as audit JSON on the order — a discount without its breakdown is unexplainable support debt.
- **Addons are child orders; the family is the unit:** merged, deduped addon lines commit as child rows under the root (`parent_id` self-reference), each precondition-checked and quoted alone; payment allocates across the open family, cancellation sweeps the lines, contact edits cascade root → lines. One row shape for the whole family — never a second "order items" schema growing beside it.
- **Installments ride two numbers:** the deposit percent sets the first-payment floor; every payment clamps — `min(asked, remaining)`, positives only — so a payment can never exceed remaining nor dodge the floor; wallet balance is verified before commit for wallet pay, and every pay/cancel/stage action wraps in its own transaction returning the fresh resource.
- **Cancellation is windows + penalty, pre-agreed:** `canCancel()/canRefund()` read the snapshot flags and windows; past the free window the stamped penalty applies; refund clamps to `paid − refunded − costs − penalty`; settlement writes ledger entries — never arithmetic edits on balance columns.
- **Test the funnel as tables:** precondition rows, discount quadrants (stackable × better-for-client × capped), the capacity race (two commits at capacity 1 — exactly one wins), provider live-guard refusals, family allocation math, snapshot immutability after a policy edit — the happy path is one row.

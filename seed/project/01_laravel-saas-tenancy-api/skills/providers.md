# Providers

The booking-provider port of this core — the concrete surface behind which paximum/viator/booking-shaped aggregators live.

- **The port's shape:** `Support/Provider/` = the abstract `Adaptor` (bind + client + request + sync + availability + book/confirm/cancel) · one concrete adaptor per aggregator, named bare (`Paximum`, `Viator`, `Booking`) · the shared `Writer` (normalized-shape → items-family upsert) · the `Mock` adaptor for the suite. Business code resolves an adaptor from the provider ROW and speaks the port's verbs — an aggregator's name appearing outside this folder (beyond stored refs) is the leak to hunt.
- **A provider is a row, an adaptor is its brain:** the `providers` table holds identity, encrypted credentials, mode (sandbox/live), enabled types, and sync state (last run, cursors, health) — the adaptor `bind()`s to a row and builds its HTTP client lazily from the row's credentials with tight timeouts; per-tenant provider accounts and multiple accounts of one aggregator are rows, never code.
- **Imported items ride the same items family:** the Writer upserts into the catalog by `(provider_id, provider_ref)` with the type/archetype resolved from the provider's category mapping (data on the provider row) — an imported hotel IS a local item with a provider origin; the funnel, permissions, and engagement machinery never know the difference. Local-only fields (tenant pricing markup, visibility, curation) live beside the synced fields and survive re-sync by the field-policy map.
- **The booking leg swaps by origin:** local items confirm by local commit; provider items run the full saga — local intent `pending` → port `book(ref, context)` → provider reference recorded → confirm on the provider's answer/webhook → the order timeline shows the provider leg's real state. Markup/commission math happens in the pricing pipeline BEFORE the provider leg (the provider sees its price, the ledger records both sides).
- **Availability is two-tier by design:** synced snapshots serve search/browse (age-labeled where short-tolerance); the commit step calls `availability(ref, context)` live through the port and re-prices — a provider "yes" older than the commit's own seconds never books; the refusal path offers the funnel's alternatives, not an error.
- **Provider webhooks land per-adaptor:** each adaptor parses and verifies its aggregator's callback dialect, translates to the port's domain events (booking confirmed/failed/amended), and the saga consumes its OWN events — amendments and provider-side cancellations enter as transitions with the provider's evidence attached.
- **Health is per-provider operational truth:** sync outcomes, request error rates, availability-check latency, booking success ratio — on the provider row and a panel surface; a degraded provider auto-degrades gracefully (its items browseable, commits refused with the honest state or failed over where an equivalent source exists) — the platform's promise survives any one aggregator's bad day.
- **The Mock adaptor drives the suite:** fixture catalogs per type, scripted availability/booking scripts including the pathological ones (timeout-then-confirmed, duplicate callback, amend-after-confirm), failure triggers by ref pattern — the whole provider machinery (sync, saga, webhooks, sweeper) tests green offline; real-adaptor translation tests ride the injectable HTTP handler with recorded provider payloads.
- Onboarding an aggregator is a bounded recipe: one adaptor class (pulls + translation + webhook dialect) + a provider row + the category/field mapping data + the sandbox matrix green — measured in days, touching zero business code; that bound IS the port's success metric.

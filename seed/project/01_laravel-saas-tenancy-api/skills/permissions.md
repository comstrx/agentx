# Permissions

Implementing and operating the cascading authority-locked permission engine — the craft over the schema in `data.md`.

- **Resolution returns a verdict object, never a bare bool:** `{ allow, locked, source }` — `allow` gates the action, `locked` gates editability, `source` names which scope decided (for the panel's fade + support's "why can't I"). One resolver function is the ONLY reader of the cascade; everything (middleware, scopes thread, panel payload) consumes its verdicts.
- **The resolution walk, fail-closed:** (1) the highest-authority `locked=true` match wins immediately — super's locks are law; (2) else the most specific `allow` match: item+actor → item → entity(role) → entity(resource type) → tenant → global; (3) else the catalog's default; (4) else DENY. No match never means allow; an unreadable cascade row means deny + a loud log.
- **Caching is per-actor and revocation-keyed:** the resolved permission map for (tenant, user, role) caches with tags fired by ANY `permission_settings` write in that scope — a super flipping a lock propagates on the next request, not the next TTL; caching verdicts longer than the cascade's write path invalidates is a privilege-escalation window.
- **The `has:` middleware consumes derived keys:** route blocks pass `has:view_products`-shaped keys; the engine derives the quartet from resource segments so a new resource's permissions EXIST the moment its routes register — hand-registering CRUD keys is drift; only cross-cutting flags (`allow_statistics`, `allow_export`) are authored into the catalog.
- **The panel contract is the verdict map, shipped whole:** the actor's bootstrap payload carries their resolved map (key → {allow, locked}) — the frontend renders from it (hide/fade/enable) and NEVER decides from it; every mutation re-verifies server-side, and a mismatch (UI allowed, server denied) is logged as a drift signal, not shrugged.
- **Lock semantics cascade downward only:** a tenant's own lock binds its entity/item scopes but never argues with super; writing a setting the resolver would ignore (tenant overriding a super lock) is REJECTED at write time with the source named — silently accepting dead rows turns the settings table into archaeology.
- **Authoring rules keep the cascade small:** write the MOST GENERAL scope that expresses the intent (a tenant-wide value, not 400 item rows), prune item rows when an entity rule supersedes them, and cap per-scope row counts with a monitored metric — a cascade that grows without pruning resolves slower and reads like sediment.
- **The two-key trap to hunt:** `allow` and `locked` are independent axes — locked+deny (super forbade, tenant sees faded off) vs locked+allow (super mandated, tenant sees faded on) vs unlocked+deny (default off, tenant may enable); conflating "locked" with "denied" in ANY consumer is the classic misread, and the test matrix covers all four quadrants per scope.
- **Test the cascade as a truth table:** rows = scope shapes (global/tenant/entity/item ± actor ± locked ± authority), columns = expected {allow, locked, source} — one table-driven suite, plus the isolation cases (tenant A's rows invisible to tenant B's resolution) and the fail-closed cases (empty cascade, unknown key ⇒ deny).
- Generalize this engine, never import one: the cascade + authority + lock model IS the product's governance feature (supers selling managed tenants depend on it) — an external RBAC package models none of it and would be a second permission truth to reconcile forever.

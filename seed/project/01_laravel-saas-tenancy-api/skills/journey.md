# Journey

The two-axis order lifecycle — commercial status × fulfillment stage — and the machine that walks it.

- **Two axes, never conflated:** `status` is the commercial lifecycle every order shares (`pending → confirmed → completed | cancelled`) — payment and settlement machinery read it; `stage` is the fulfillment journey only some archetypes have (application processing, policy issuance, check-in) — operations walk it. Collapsing them into one column is how "cancelled but issued" becomes representable.
- **The stage machine derives from capabilities:** the item's capability set → a journey shape (`processed`, `underwritten`, `perishable`, `instant`) → an adjacency map `from => [allowed next]` per shape. A new archetype adds a shape + map; zero transition code changes — the same anti-literal law, applied to workflow.
- **Transition is ONE guarded door:** status must permit staging at all → look up `machine[from]` → anything unlisted refuses fail-closed (INVALID_STATE on the `stage` field) → per-stage payload rules enforced (scheduling demands a valid future datetime) → persist quietly → flush the cache tag → journey-log → domain event `order.stage.<x>` → notify participants (`afterCommit`, best-effort, caught + logged). Every stage write goes through this door; a second write path is a corruption vector.
- **Raw values guard, casts express:** the machine compares `getRawOriginal('stage'|'status')` — stored truth — while domain helpers speak the enum casts; mixing the two comparison styles is the silent-false classic.
- **The journey log is the audit spine:** every status/stage change appends `{event, from, to, actor, ip, agent, at}`; the client-facing `timeline()` is a projection over the log — never a parallel table, never reconstructed from `updated_at` archaeology.
- **Stage consequences settle beside the transition, same transaction:** rejected → the refund settlement; issued/delivered → completion — one named settle step next to the transition call, not reactions scattered through controllers.
- **Provider stages translate into the SAME vocabulary:** an externally-fulfilled order's provider state maps through the adaptor's tracking into this machine's stages — the operator sees one journey whether fulfillment is local or a provider's.
- **Check-in is a stage with a secret:** perishable orders carry a per-tenant-unique secret key (the QR payload); check-in resolves the order by key or id and transitions through the same door — the scanner endpoint earns zero special-case machinery.
- **The machine ships its verifier and reconciler:** `journey:verify` asserts every stored stage is reachable in its shape's machine; the scheduled reconciler surfaces stages stuck past SLA to operators — a state machine without its verifier drifts the day someone hot-fixes a row.
- Test as a truth table: shapes × from × to (allowed and refused), the settle side-effects, the two-axis independence (cancellation during any stage), and the timeline projection — minutes of tables covering what incidents teach in weeks.

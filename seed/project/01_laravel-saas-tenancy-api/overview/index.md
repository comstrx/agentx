# Index

- **What this is:** the universal multi-type SaaS core — one headless Laravel API serving multi-tenant, multi-vendor marketplace/booking platforms. One codebase, forked per client; only the client-facing surfaces differ. It fuses the booking.com / airbnb / viator / freelance-marketplace shapes into one clean engine.
- **The bounded universe — exactly these types, ERP excluded:** physical products · digital products · offline services · online services · courses · books · hotels · rooms · realestate · tours · visa · events · conferences · travels. Fourteen types, one `items` family, uniform DNA — a new vertical is a type row + capabilities, never a new module.
- **The actors:** super (platform owner, cross-tenant, audited) · admin · vendor · affiliate · delivery · client. Every actor except the client works through the admin panel; the client lives on the site + mobile app. Each panel role has its super/supervisor/member tiers — all derived from permissions, never boolean columns.
- **The surfaces:** a versioned `/v1` JSON API, per-panel route files, stateless Bearer tokens bound to tenants, the `routes/collections/` mirror as the living API contract consumed by the admin/site/app teams.
- **What "done" means here:** a new resource costs ~4 declarations and materializes its full gated API; a new tenant provisions in one flow; a new type is data; the gate (analyzer + suite) is green; the collections mirror moved in the same change.
- **The non-negotiables in one breath:** tenant isolation fail-closed at the lowest layer · capability-branching (zero type/role literals in core) · money as double-entry integer ledger · every lifecycle a guarded state machine · providers behind ports with the local-first saga · Octane-safe request state — all law, all inherited from the training chain, all enforced in review.
- **The moat to protect:** the multi-type capability. Every change is judged first by one question — does this keep the core type-agnostic and additive, or does it leak a vertical into the DNA?

# State

The runtime dotdir — the tool's memory between invocations; its shape is a contract with the user and with every future version.

- **One dotdir, declared and owned:** all runtime state under a single named dotdir (project-local for per-project tools, home-rooted for global ones — the tool's charter says which); every dir and file name inside is a const, and the README admits the dotdir exists — a tool that scatters state it never documents is a bad guest.
- **`init` scaffolds it idempotently:** creates the full skeleton, completes what is missing, NEVER overwrites what exists — running `init` twice is a no-op; running it on a half-broken dotdir repairs the skeleton and touches nothing user-authored.
- **State files are typed, versioned documents:** one schema per file (the journey/state document, the config document), serialized human-readable, carrying enough shape that a future version can read an old file — load is fail-safe (unparseable → explicit error naming the file and the fix, or a documented fresh-default; never a silent half-parse).
- **Every write is atomic:** write to a temp sibling, rename into place (same-directory rename — no cross-filesystem surprises) — a kill at ANY instruction leaves either the old state or the new, never a torn file; the next run trusts what it reads because this law has no exceptions.
- **The lock protocol:** one pid-file lock acquired by atomic create; a stale lock (dead pid) is taken over by rename (exactly one winner under race); an alive holder means a clear "already running" error with the pid — lock release rides every exit path including the violent ones, and a crashed run's lock never demands manual cleanup.
- **Resumability is the state's purpose:** the state document records progress as durable checkpoints (phase, cursor, completed items) written AT each transition — a resumed run continues from the cursor, never redoes completed work, and re-derives nothing it already ruled on; "resumable" is proven by kill-and-restart tests, not claimed.
- **Status reads only, and reads everything:** the `status`-shaped command renders the state document + live signals (lock holder, log tail) without mutating anything — the user can always ask the tool what it believes is true; a status that writes is a heisenberg tool.
- **Doctor verifies the world, state included:** schema-valid state files, lock sanity, tool-version vs state-version compatibility — with named fixes for each failure; `reset`-shaped destruction always confirms (the interactivity law) and names exactly what dies.
- **Logs are state too:** the run log lives in the dotdir, plain and append-only (pipe-clean content — the styled UI is the terminal's, the log is the record); rotation/pruning is the tool's job with a declared cap, never the user's surprise disk bill.
- Cleanup discipline: transient artifacts (temp files, spawned-process registries) are removed on clean exit AND swept on next start — the dotdir's steady-state contents are exactly the documented set; anything else found there is a bug with a filename.

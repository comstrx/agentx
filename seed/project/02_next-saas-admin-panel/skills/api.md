# Api

Driving the typed endpoint registry — this panel's concrete data machinery over the API.

- **The entry is the atom:** every endpoint is an `ApiEntry` — `resource`, `action`, `method`, `path`, `need` (the permission key that gates it), optional `schema` (the Zod shape that validates its response), optional flags (`bare` = no envelope, `guest` = no session) — declared in `src/api`, consumed everywhere, written nowhere else. A URL string inside a feature is the defect the registry exists to kill.
- **`resource(name, { schema, extra })` materializes the CRUD set:** list/show/store/update/destroy entries with paths, methods, permission keys (`products.list`-shaped), and array/single schemas derived from ONE declaration — bespoke endpoints ride in `extra`; the registry composes resources + standalone entries into the `api` object that IS the client's surface.
- **The client executes entries, not requests:** one `call(entry, { params, body, id })` — base URL, session cookies, tenant/locale headers, envelope unwrapping, Zod validation of the response, and error normalization all live there; a feature never touches `fetch`, never parses an envelope, never builds a header.
- **Query keys derive from entries:** `[entry.resource, entry.action, params]` — one key factory, so invalidation is mechanical: a mutation on a resource invalidates that resource's list/show families; hand-written string keys drift from the registry and orphan caches.
- **`need` wires the registry to the permission map:** the `can(entry.need)` gate wraps the buttons/columns/menu items that would call the entry — UI gating and API gating share ONE key vocabulary (the backend's derived quartet + flags), so a permission change reshapes the panel with zero code, which is the panel's whole thesis.
- **Schemas are the boundary law:** an entry with a schema rejects a drifted response at the edge (loudly, in dev; logged, in prod) — the panel discovers API contract drift at the first call, never at a deep component's `undefined`. Schemas live beside entries and derive their TS types; a hand-written interface for a response shape is parallel truth.
- **Mutations return the envelope's verdict:** field errors map into react-hook-form by key (the form's names mirror the API's), refusal keys map to UX in one translator (toast/inline/redirect) — per-form error improvisation is a leak; the translator is the only reader of raw failure shapes.
- **Tables and forms consume entries whole:** the table engine takes a list entry + column defs (server-driven pagination/sort/filter riding the entry's params); the form engine takes store/update entries + the field map — a screen is entries + declarations, which is why adding a resource to the panel is a morning's work.
- **The collections mirror is the upstream truth:** entries transcribe the API's `routes/collections/` contract — a backend API change lands here as an entry/schema diff in the SAME change cycle; a drifted entry is a broken build, not a runtime surprise.
- Test the machinery, not each screen: the registry's suite validates every entry's shape, the key factory's derivations, and the client's envelope/error handling against fixture responses — screens then trust the machinery and test only their declarations.
